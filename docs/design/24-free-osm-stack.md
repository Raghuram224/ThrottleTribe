Source: user decisions, 2026-10-16: *the app must cost $0 and stays on OpenStreetMap.* (1) Basemap moves from Positron to

## 0. Summary

**Purpose:** the same app on a map with more to read (roads, places, labels), at no cost, with search and routing that keep
working when a free quota runs out.

**One-second glance (unchanged, 20 / 21):** 1. anyone in trouble → 2. where each rider is → 3. next turn / distance to the
stop. **New rule for the basemap:** the route line and the rider markers are always the strongest things on the map. More
map detail must never beat them.

### 0.1 The stack
| Service | Used for | Free limit (checked 2026-10-16) | How we call it | Credit required |
|---|---|---|---|---|
| OpenFreeMap | Vector tiles, sprites, fonts | none published (fair use; offline packs ≤ 3,000 tiles) | Phone, direct (no key) | none required; we credit it in the Credits sheet |
| OpenMapTiles schema | Tile schema / style design | — | — | "© OpenMapTiles" |
| OpenStreetMap | All data | — | — | "© OpenStreetMap" (or "contributors") + a way to reach the licence |
| **Geoapify** | Typed search (Autocomplete), chips (Places) | 3,000 credits/day, 5 req/s; soft limits, **overage may be charged** | Edge Function `geo` (key secret) | "Powered by Geoapify" with a link, near the results |
| **Photon** (komoot) | Fallback search | fair use, throttled when heavy | Phone, direct (no key) | none stated; we credit "Photon" + OSM |
| **LocationIQ** | Directions, `driving`, `steps=true` | 5,000/day, 60/min, 2/s; hard `429` | Edge Function `geo` (key secret) | "prominent link back", format "Search by LocationIQ.com" |
| Supabase Edge Functions | Proxy, quota counters | Free plan invocations (verify current number) | — | — |

**$0 guarantee:** Geoapify's terms allow overage charges, so the function enforces a **hard cap below the free quota**
(§5.2) and switches to Photon before Geoapify's limit is reached. LocationIQ's free plan hard-stops with `429`.

## 2. Search (overturns 19 A "Search (client)", 21 §2.2 attribution)

### 2.1 Provider chain
```
typed text (≥ 3 chars, 400 ms) ─┐                          ┌─ 200 → results, credit "Powered by Geoapify"
chip tap (at once) ─────────────┼─► Edge Function geo ─────┤
                                │   (≤ 4 s client timeout) └─ 429 / 5xx / timeout / unreachable
                                │                                   │
                                └───────────── Photon, direct ◄─────┘ (≤ 6 s) → results, credit "Search: Photon"
                                                                     └─ fails → busy / error state (§2.5)
```
- **Sticky fallback:** `quota` (Geoapify daily cap or `scope: 'day'`) → every search goes straight to Photon for 30 min, then one
  probe goes to the function again. `second` / `minute` / timeout / 5xx → only that request falls back. Function unreachable
  while Photon answers → sticky for 5 min. In memory only.
- One result set comes from **one** provider (never mixed). A chip widen that fails keeps the first set.
- Viewer offline (`useNetOffline`): no request at all; offline state (§2.5).
- In-memory cache: 20 queries (exists), keyed without the provider; a hit keeps the provider it came from (for the credit).

### 2.2 Typed search (Geoapify Autocomplete)
- Function forwards to `GET https://api.geoapify.com/v1/geocode/autocomplete` with `text`, `bias=proximity:<lon>,<lat>`
  (position rounded to **2 decimals** on the phone, 21 §5.6), `limit=8`, `lang=en`, `format=json`. No country filter
  (riders cross into Nepal, Bhutan). 1 credit per request.
- Order: relevance (as today). Distance column from the phone's exact fix (haversine), as today.
- `SEARCH_DEBOUNCE_MS` 350 → **400**; `SEARCH_MIN_CHARS` 3 (unchanged); in-flight abort (exists).

### 2.3 Chips (Geoapify Places)
`SEARCH_CHIPS` gains `categories`:
| Chip | `categories` | Photon fallback (unchanged) |
|---|---|---|
| Coffee | `catering.cafe` | `amenity:cafe` / "cafe" |
| Fuel | `service.vehicle.fuel` | `amenity:fuel` / "petrol" |
| Food | `catering.restaurant,catering.fast_food` | `amenity:restaurant` / "restaurant" |
| Parking | `parking.cars,parking.motorcycle` (verify both keys exist; else `parking` and drop results whose only category is `parking.bicycles`) | `amenity:parking` / "parking" |
| Toilets | `amenity.toilet` | `amenity:toilets` / "toilet" |
- Request: `GET https://api.geoapify.com/v2/places` with `categories`, `filter=circle:<lon>,<lat>,<radiusM>`,
  `bias=proximity:<lon>,<lat>`, `limit=20` (20 places = 1 credit), `lang=en`. Position rounded to **3 decimals** (≈ 110 m) on
  the phone: a 5 km circle centred 1 km off would miss the nearest pumps.
- **Radius (S5):** 5,000 m. If fewer than 3 named places → one more request at 25,000 m (1 more credit) and that set replaces
  the first. Never more than 2 requests per chip tap.
- **Ranking:** drop unnamed places, compute haversine from the **exact** fix, sort nearest first (`sortByDistance`, exists),
  show the first **10**.
- Photon fallback: as today (`osm_tag` + query + 2-decimal bias), sorted by distance, **dropping anything beyond 25 km** so both
  providers mean the same "nearby".
- Caption above chip results (new, 32 dp row, 14 regular `textMuted`, tabular): `search.chipWithin` "Nearest first · within
  5 km" (or 25 km). Empty after widening: `search.chipEmpty` "No {chip} within 25 km" (chip label lower-cased).

### 2.4 Place model and recents
- `Place.source: 'geoapify' | 'photon'` (new). Ids: `g:<place_id>` / `p:<osm_type><osm_id>` (Photon keeps today's form with the
  `p:` prefix). Name: `name`, else `address_line1`. Address: `[street + housenumber, city]` as Photon today (not Geoapify's long
  `address_line2`). Category from `categories`: `catering.cafe*` → cafe · `service.vehicle.fuel*` / `commercial.gas*` → fuel ·
  `catering.restaurant*` / `catering.fast_food*` / `catering.food_court*` → restaurant · `parking*` → parking · `amenity.toilet*`
  → toilets · else other.
- `recent-places.ts` stores `source`; entries without it parse as `'photon'` (they were). The place sheet's credit line uses it (§4.2).

## 3. Routing (overturns 19 A "Route to the stop" provider, 21 §3.1 URL / §5.1; closes 21 D1)

### 3.1 Request
- The app calls the function `geo` with `{ op: 'route', from, to, steps, bearingDeg? }`. `from` and `to` are exact (routing
  needs them; `locBody` says so). The function calls
  `GET https://<region>.locationiq.com/v1/directions/driving/<lng,lat>;<lng,lat>?key=…&overview=full&geometries=geojson&steps=<bool>`
  plus `&bearings=<deg>,45;` when given (LocationIQ documents `bearings`). It returns LocationIQ's OSRM-shaped JSON
  **unchanged** (`code`, `routes[].geometry/distance/duration/legs[].steps[]`), so `parseOsrmResponse` and the 21 §3 engine
  keep working. `NoRoute` comes back as HTTP 200 `{ code: 'NoRoute' }`.
- `exclude` is **not documented** by LocationIQ, so `flags.ROUTING_SUPPORTS_EXCLUDE` stays off (21 D2a): no expressway switch,
  the standing note `preview.carNoteMayUse` "Route for cars — may use expressways that ban two-wheelers." stays on every
  route preview. (§13.5: test whether LocationIQ honours `exclude=motorway`.)
- **Car profile, said in copy:** LocationIQ `driving` is a car profile, like the OSRM demo (21 §5.2): it can use access-controlled
  expressways that ban two-wheelers (the Bengaluru–Mysuru Expressway, NH275). ETAs are car ETAs. Nothing in the app may say
  "bike route" or "motorcycle route"; the car note is the only place the profile is named. Voice and banner text are
  unchanged (they never name a vehicle).
- `EXPO_PUBLIC_ROUTING_URL` stays as a **development** override (direct OSRM-shaped server, no credit change in dev). Production
  builds ignore it and always use the function. Client timeout 8 s (exists); the function's upstream timeout 7 s.

### 3.2 Budget (why throttling matters)
LocationIQ free: **2/s, 60/min, 5,000/day, app-wide** (one key for every rider). Expected use:
- Solo navigation: 1 preview (seeded into live, 21 §2.3) + reroutes (≥ 10 s apart, only while off route).
- Group with a stop: 1 request per rider per stop change + the 19 A 60 s off-route rule per rider.
- A `stop_set` reaching 10 riders at once is 10 requests in one second: 5× the per-second limit. Hence the jitter below.

### 3.3 Engineer rules (client)
| Rule | Value |
|---|---|
| Navigating reroute (21 §3.8) | unchanged: ≥ 10 s apart, backoff 10 / 20 / 40 / 60 s, at most 1 request in flight, plus: next attempt ≥ `retryAfterS` |
| Group stop route (not navigating) | unchanged 60 s rule; **new:** after `stop_set` or a reconnect, wait a random **0–5 s** before the first fetch (spreads a group's burst) |
| Preview | unchanged: 500 ms settle, one request per route mode, 5 min / 4 entry cache |
| `429` `scope: 'second'` | one automatic retry after 1 s; **not** counted as a failure for the backoff |
| `429` `scope: 'minute'` or `'user'` | wait `retryAfterS` (≤ 60); counts as a failure (`failures += 1`) |
| `429` `scope: 'day'` | `routingPausedUntil = now + 30 min` (module memo, every caller reads it): no route requests; then one probe |
| Any failure | keep the last good route drawn; never clear it on a failed reroute (exists) |
| Cache | LocationIQ allows caching responses for 48 h; our 5 min client cache stays. No server cache in v1 |
`nav-route.ts` `NavRouteResult` gains `{ status: 'rate_limited'; scope; retryAfterS }`; `nav.route_failed` code gains
`rate_limited`. `shouldFetchNavRoute` / `shouldRerouteNav` take `notBefore = lastFetchAt + max(backoff, retryAfterS)`.

## 5. Edge Function `geo` (behaviour; engineer owns the code)

### 5.1 Contract
`POST /functions/v1/geo`, JSON, `verify_jwt` on (signed-in or guest session only), CORS for the web origin.
| `op` | Body | 200 response |
|---|---|---|
| `autocomplete` | `{ text, near?: {lat,lng} (2 dp), limit: 8 }` | `{ provider: 'geoapify', places: PlaceDTO[] }` |
| `places` | `{ categories, near: {lat,lng} (3 dp), radiusM: 5000 \| 25000, limit: 20 }` | `{ provider: 'geoapify', places: PlaceDTO[] }` |
| `route` | `{ from, to, steps, bearingDeg? }` | LocationIQ JSON as is, header `x-geo-provider: locationiq` |
Errors: `429 { error: 'rate_limited', scope: 'second'\|'minute'\|'day'\|'user', retryAfterS }` (search day cap → `scope: 'day'`),
`502 { error: 'upstream' }`, `504 { error: 'timeout' }`, `400 { error: 'bad_request' }`. Upstream LocationIQ `429` messages map
"Rate Limited Second/Minute/Day" → the same scopes.
`PlaceDTO = { id, name, street, housenumber, city, lat, lng, categories }`: normalised server-side, so the phone parses one shape.

### 5.2 Caps (enforced by the function before calling upstream; counters in Postgres, atomic)
| Provider | App-wide cap | Provider limit | Per user (anonymous: half; plus per address 60 / 20 per min) |
|---|---|---|---|
| Geoapify | **2,800 credits / UTC day**, 4 req/s | 3,000 / day, 5 req/s (soft; overage may be charged) | 30 search req / min, 400 / day |
| LocationIQ | **4,800 req / day**, **50 / min**, **1 / s** (wait up to 1 s for a slot before answering 429 `second`; fixed windows can double up at a boundary) | 5,000 / day, 60 / min, 2 / s | 12 route req / min, 200 / day |
- `retryAfterS`: second → 1; minute → seconds to the next minute; day → seconds to the next UTC midnight (the client caps its
  pause at 30 min and probes).
- Logs: op, provider, status, latency, cost. **Never** coordinates, text, place names or user ids.
- Secrets `GEOAPIFY_API_KEY`, `LOCATIONIQ_API_KEY` via `supabase secrets set`; never `EXPO_PUBLIC_*`, never in git.
- Dev only: `EXPO_PUBLIC_GEO_SIMULATE` = `search_429` | `search_quota` | `route_429_minute` | `route_429_day` makes the
  client behave as if the function answered that way (for §11 tests). Ignored in `preview` / `production` profiles.

- The function answers `503 { error: 'not_configured' }` for a missing provider key and `503 { error: 'counters_unavailable' }` for missing or failing counters (a plain failure for the client); the client treats not_configured and a 404 (not deployed) as "not configured": search goes to Photon (sticky 30 min), routing to the OSRM URL (remembered 10 min).

- `ROUTING_SUPPORTS_EXCLUDE` only means something for a direct router: `geo` never forwards `exclude`. Keep it off with `geo`.
- Spec figure check: the motorway / trunk / primary casing is 18.3 at z19 (as written); local street casings (`bridge_street_casing`, `road_minor_casing`) grow past the route casing from about z18.5, which §1.4 does not cover.
